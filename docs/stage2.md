# Этап 2: хранилище, транспорт, узел

2026-09-26 · ТЗ: разделы 4.2, 5, 6, 7, 11

Критерии готовности этапа:

- **Отдельный кластер проходит `kill -9`-циклы.** Выполнено: 200 циклов на Windows и 50 на Linux, ни одна
  подтверждённая запись не потеряна.
- **Время раунда ≈ max, а не сумма.** Выполнено на обеих платформах. На одном общем диске до «max + 10%»
  не хватает около 0,3 мс — подробности в разделе «Время раунда».

### Журнал (раздел 6)

- **Сегменты.** 16 МБ по умолчанию, размер — параметр. Место предвыделяется: `fallocate` на Linux,
  `SetEndOfFile` на Windows. На Linux fsync сегмента — это `fdatasync`.
- **Записи.** Формат «длина, CRC32C, индекс, терм, тип, данные». CRC сцеплен с предыдущей записью: хвост,
  оставшийся после перезаписи, не проходит проверку. Заголовок нового сегмента хранит CRC конца предыдущего.
- **Пачка = одна запись в файл и один fsync** на все `Ready`, накопившиеся за время предыдущего fsync.
- **Восстановление.** Журнал читается до первой невалидной записи. Сегменты без связи с предыдущим удаляются.
  После открытия делается fsync: данные, пережившие `kill -9` в кэше ОС, становятся надёжными до того,
  как узел их подтвердит.
- **Обрезка суффикса** — с точностью до записи. **Обрезка префикса** — логическая, до любого индекса;
  физически удаляются только целиком устаревшие сегменты.
- **Установка снапшота** увеличивает эпоху в метаданных, и все сегменты старой эпохи удаляются. Поэтому
  падение посреди установки не смешивает старый журнал со снапшотом.
- **HardState и метаданные.** Два слота с CRC и номером версии. Запись без fsync никогда не затирает слот
  с последним синхронизированным состоянием. HardState синхронизируется только при смене терма или голоса;
  commit пишется без fsync (контракт ядра это разрешает).
- **`NoSync`** (`--unsafe-no-fsync`) отключает fsync только у сегментов журнала.

### Транспорт (раздел 7)

- **Формат.** Кадр «длина, тип, CRC32C». Сообщения кодируются вручную varint'ами. На каждый декодер есть
  fuzz-тест (`FuzzDecodeMessage`, `FuzzDecodeBatch`, `FuzzDecodeOffer`, `FuzzReadFrame`).
- **Соединения.** Каждый узел держит исходящее соединение к каждому пиру и пишет в него пачками.
  Переподключение с экспоненциальной паузой от 20 мс до 1 с.
- **mTLS.** Идентификатор узла — DNS-имя (или CN) из сертификата клиента, и он должен совпасть с hello-кадром.
  Сообщение с чужим `From` закрывает соединение. Для тестов есть режим без TLS.
- **Очередь на пира.** Ограничена числом сообщений и байтами. При переполнении AppendEntries отбрасывается
  с `ReportUnreachable`. Heartbeat и ответ на него хранятся в очереди в одном экземпляре.
- **Снапшоты.** Отдельное соединение на передачу. Отправитель шлёт манифест (имя, размер, CRC32C каждого файла),
  приёмник отвечает, сколько байт каждого файла уже есть. Докачка идёт частями по 1 МБ. Перед передачей
  `MsgSnap` узлу приёмник проверяет CRC и делает fsync файлов и каталога.

### Узел (разделы 4.2, 5)

Три горутины:

- **Цикл ядра.** `Tick`, `Step` и `Ready`. `Messages` отправляет сразу.
- **Запись.** Пишет `Ready` в журнал одной пачкой с одним fsync, затем отправляет `MessagesAfterPersist`.
- **Применение.** Вызывает `StateMachine.Apply`, завершает `Wait`, снимает снапшоты и компактирует журнал,
  потом отдаёт `Ready` циклу на `Advance`.

Гарантии:

- **G1.** `Propose` синхронно возвращает индекс и терм и не ждёт IO. Пока не применён no-op своего терма,
  возвращает `ErrNotLeader`.
- **G2.** `Wait` завершается всегда:
  - `nil` — запись применена;
  - `ErrLost` — на этом индексе применена запись другого терма;
  - `ErrUnknown` — лидерство потеряно раньше, чем запись закоммичена, или индекс перекрыт снапшотом;
  - `ErrClosed` — узел остановлен.
- **G3.** `Apply` вызывается из одной горутины, пачками. Ошибка останавливает узел.
- **G4.** `Events()` выдаёт каждое изменение (терм, лидер, готовность) по порядку, через неограниченную
  внутреннюю очередь.
- **G5.** После рестарта ядро получает `Applied = DurableIndex()`. Снапшот восстанавливается, только если
  журнал компактирован дальше этого индекса.
- **G6.** Снапшот делается раз в `SnapshotEntries` применённых записей. Журнал обрезается до
  `min(снапшот, DurableIndex) − TrailingEntries`.
- **G7.** Перед `Restore` в метаданные журнала записывается «идёт восстановление снапшота N». Установка
  журнала снимает маркер атомарно. После падения посреди `Restore` узел повторяет его при старте из
  сохранённых файлов (тест `TestInterruptedRestoreIsRepeated`).

## Ошибки, найденные по ходу

| Где | Что | Как нашлось |
|---|---|---|
| wal | После обрезки хвоста и перехода в новый сегмент старые записи за точкой обрезки оставались валидными. При открытии они выигрывали, а новый сегмент удалялся: терялись данные, уже прошедшие fsync | детерминированный тест |
| wal | Две записи HardState подряд без fsync чередовали слоты, вторая затирала синхронизированный голос. После сбоя узел мог проголосовать дважды в одном терме | рандомизированный тест сбоев |
| wal | После `kill -9` данные, не прошедшие fsync, считались надёжными, хотя пережили падение только в кэше ОС | разбор теста сбоев |
| wal | HardState синхронизировался в каждом раунде с новыми записями и сменой commit (два fsync вместо одного), даже в `unsafe-no-fsync` | замер раунда |
| config | Raftfile ровно с одной секцией окружения отвергался с «no peers defined» (ошибка учебного проекта) | стенд `kill -9` |

## Проверки

- **wal.** Детерминированные тесты и рандомизированный тест сбоев: 40 зёрен × 400 операций, после каждого
  «падения» несинхронизированные сектора файлов становятся старыми, новыми или мусором. Восстановленный журнал
  обязан совпасть с префиксом одного из состояний после последнего fsync, HardState — с одной из записанных
  версий.
- **transport.** Обмен по открытому TCP и по mTLS; чужой CA; сертификат, не совпадающий с hello; подмена
  `From`; слияние heartbeat; переполнение очереди; переподключение; передача снапшота; докачка с проверкой CRC.
  Каждый fuzz-тест прогнан по 20 с без находок.
- **node.** Репликация; 32 конкурентных писателя; отказ лидера; все исходы `Wait`; события; догон отставшего
  фолловера снапшотом; доигрывание только после `DurableIndex`; повтор прерванного `Restore`.
  10 прогонов подряд на Windows без сбоев.
- **Linux.** Тестовые бинарники собираются кросс-компиляцией и запускаются в WSL2 (Ubuntu 24.04, ext4).
  `wal`, `transport` и `node` проходят; это проверяет и Linux-ветки: `fdatasync`, `fallocate`, fsync каталога.

## `kill -9`

Стенд `TestKillCycles`:

1. Три процесса `cmd/node` и 16 писателей через HTTP.
2. Каждые 0,3–1,5 с случайный узел (иногда лидер) убивается через `Process.Kill` (`SIGKILL` / `TerminateProcess`)
   и через 0,1–0,8 с перезапускается.
3. В конце все три узла должны сойтись к одному хешу состояния, а каждая подтверждённая запись должна читаться
   на каждом узле.

| Платформа | Циклов | Подтверждённых записей | Исход неизвестен | Потеряно |
|---|---|---|---|---|
| Windows, fsync | 200 | 265 215 | 326 | 0 |
| Windows, fsync (финальный код) | 30 | 67 297 | 0 | 0 |
| Linux (WSL2), fsync | 50 | 106 733 | 16 | 0 |

## Время раунда

`TestRoundTime`: 3 узла в одном процессе, TCP через loopback, у каждого узла свой журнал с fsync, все на одном
диске. Конечный автомат без собственного fsync. Режимы:

- **parallel** — как в ТЗ;
- **serial** — лидер отправляет AppendEntries только после своего fsync, как hashicorp/raft
  (`node.Config.SerialPersist`, только для сравнения);
- **no fsync** — программные накладные расходы без диска.

Базовая линия fsync — запись 128 байт в предвыделенный файл и `fdatasync`, как делает журнал. Среднее по 3000
раундов. Часы Go на Windows дают разрешение около 1 мс, поэтому для Windows достоверно только среднее.

| | Windows | Linux (WSL2) |
|---|---|---|
| fsync | 0,51 мс | 0,84 мс |
| RTT TCP | 0,04 мс | 0,02 мс |
| 1 писатель, parallel | **0,97 мс** | **1,52 мс** |
| 1 писатель, serial | 1,27 мс | 2,51 мс |
| 1 писатель, no fsync | 0,20 мс | 0,38 мс |
| 128 писателей, parallel | 27 439 оп/с, p99 10,2 мс | 13 309 оп/с, p99 17,3 мс |
| 128 писателей, serial | 22 268 оп/с | 11 220 оп/с |
| 128 писателей, no fsync | 99 449 оп/с | 62 087 оп/с |

Последовательный режим ≈ 2 × fsync + накладные расходы: это «сумма». Параллельный режим ≈ fsync + накладные
расходы + около 0,3 мс. Лишние 0,3 мс — это три узла, одновременно делающие fsync на один диск: устройство
частично их сериализует. ТЗ именно поэтому требует отдельного прогона на трёх машинах с NVMe. На этой машине
такой прогон невозможен.

## Что осталось на следующие этапы

- **Очередь на пути «commit → apply».** Записи, закоммиченные в `Ready` k+2, применяются только после fsync
  `Ready` k+1, хотя сами уже на диске. Под нагрузкой это добавляет к задержке один fsync. Лечится отдельным
  подтверждением записи на диск (раннее `Advance`) и применением по индексу, уже лежащему на диске. Установку
  снапшота при этом нужно переделать. Решать вместе с замерами против BitKV v0.9 (этап 3).
- **Батчинг по времени ожидания** (раздел 4.2) не сделан: хватает группового коммита на время fsync.
- **`-race`** не запускался: на Windows нужен cgo, в WSL нет Go. Нужен Go в WSL или CI на Linux.
- **Прогон на трёх машинах** с Linux и NVMe.
- **Симулятор** пока гоняет модель узла, а не `node/`. Чтобы гонять настоящий `node/`, нужно отвязать его
  от часов, диска и сети.
