# Этап 3: интеграция в BitKV

2026-09-26 · ТЗ: разделы 2, 5, 9, 11

Критерий готовности — «тесты BitKV зелёные на обеих реализациях, сравнение бенчмарков» — выполнен. Новая реализация
обгоняет hashicorp/raft во всех сценариях раздела 9. Цели по пропускной способности выполнены; цели по хвосту
задержек и по времени отказа лидера выполнены не полностью (см. «Что не выполнено»).

## Что сделано в BitKV

Изменения лежат в ветке `own-raft` репозитория BitKV.

- **Общий интерфейс.** `replica.Replica` с методами `Update`, `Flush`, `Status`, `Close`. Сервер и `cmd/bitkv`
  работают только с ним.
- **Выбор движка.** `replica.Open` выбирает движок по `Config.Engine`, в командной строке — флаг
  `-raft-engine=hashicorp|own`. По умолчанию пока `hashicorp`.
- **Новый движок** (`own.go`):
  - `Update` берёт терм из события готовности лидера (G4) и публикует операции через `node.ProposeIn(term, …)`.
    Индекс Raft, возвращённый синхронно, становится id спекулятивно предложенных значений в Bitcask (G1).
  - `Wait` без вспомогательной горутины: `node.Close` сам завершает все ожидания.
- **Конечный автомат** (`own_fsm.go`):
  - `Apply` склеивает операции соседних записей в один `db.Apply`, `Flush` применяется на своём месте.
  - Снапшот — жёсткие ссылки через `LinkFiles` и описание с размерами файлов. `Restore` копирует ровно эти байты,
    хотя по жёсткой ссылке активный файл продолжает расти.
  - `DurableIndex` — индекс последнего снапшота или восстановления: в этот момент база синхронизирована. Операции
    абсолютные, так что доигрывание с этого индекса идемпотентно. Точный индекс в записях Bitcask — этап 4.
- **Защита каталогов.** Каждый движок отказывается открывать каталог Raft, записанный другим, и базу с данными без
  состояния Raft.
- **Зависимость.** В `go.mod` BitKV добавлен `replace github.com/acneism/raft => ../raft`: модуль не опубликован.

Для нового движка из раздела 5 ТЗ уходят:
- терм внутри записи и `errStale`;
- счётчик готового терма и `Barrier`;
- `NoSnapshotRestoreOnStart` (его роль берёт G5);
- маркер `RESTORING` (его роль берёт G7 в `node`);
- обёртка `linkStore`;
- горутина в `wait`.

Код hashicorp пока остаётся рядом без изменений.

## Тесты

Общие тесты `internal/replica` идут в матрице «движок × fsync» без изменения смысла: `TestConcurrentWritesReplicate`,
`TestCatchUpAndFailover`, `TestHotKeyFailover`. У тестов, завязанных на внутренности hashicorp, есть пары для нового
движка:

| hashicorp | новый движок |
|---|---|
| `TestApplyBatchKeepsLogOrder` | `TestOwnApplyKeepsLogOrder` |
| `TestInterruptedRestoreResumes` | `TestOwnInterruptedRestoreResumes` (маркер G7 с чужим снапшотом, база частично стёрта) |
| `TestRefusesOldRaftLog` | `TestOwnRefusesOtherEngineDir` |

Весь набор BitKV зелёный на Windows и Linux (WSL2). `internal/replica` на Windows прошёл 5 прогонов подряд, на Linux — 2.
Исходный тест hashicorp `TestConcurrentWritesReplicate` один раз упал ещё до изменений, когда параллельно шли тесты
других пакетов; отдельно он проходит.

## Что пришлось поправить в библиотеке

| Что | Как проявилось |
|---|---|
| **Снапшоты с подкаталогами.** Манифест транспорта был плоским, а снапшот Bitcask лежит в `log-NNN/`. Теперь пути относительные через `/`, с проверкой, что путь не выходит за каталог снапшота | фолловер не мог восстановиться из снапшота |
| **`wal.Sync` держал мьютекс журнала на время fsync.** Цикл узла читает журнал под мьютексом ядра, поэтому каждый fsync останавливал цикл, а с ним `Propose`. Теперь fsync идёт без мьютекса, закрытие сегментов ждёт его отдельно | горячий INCR был в 4 раза медленнее hashicorp; после исправления — в 2 раза быстрее |
| **`node.ProposeIn(term, data)`.** Атомарная проверка терма, чтобы запись, собранная по спекулятивному состоянию терма T, не попала в журнал в другом терме (проблема 5 из раздела 2 ТЗ) | требование G1 |
| **Повтор запросов голосов и разрешение ничьей в PreVote.** Кандидат раз в интервал heartbeat повторяет запрос тем, кто не ответил. Пре-кандидат, выдавший пре-голос узлу со старшим ID, после своей победы в пре-голосовании уступает ему. Симулятор после изменения: 64 × 10⁷ шагов без нарушений | хвост времени отказа лидера до 3,7 таймаута выборов |
| **Тики по часам.** Тикер Go на Windows с периодом 2 мс реально срабатывает раз в 3,5 мс. Узел теперь вычисляет число тиков по часам и досылает недостающие. По умолчанию 10 мс × 100 тиков (таймаут 1 с, как у hashicorp): мелкие тики снижают вероятность разделённых голосов | таймаут выборов растягивался в 1,7 раза |
| **Аллокации.** Кэш журнала вытесняется порцией со сдвигом на месте, а не копированием всего кэша на каждую дозапись. Индекс журнала компактируется на месте, очередь пира в транспорте переиспользуется | −13% байт на операцию |

## Что не выполнено и почему

- **p99 ≤ 3 × p50 без fsync.** Хвост создаёт сборщик мусора. Для SET без fsync p99 при `GOGC=100` — 10–11 мс,
  при `GOGC=400` — 5,6 мс (3,0×), с выключенным GC — 4,5–6,2 мс. Основная доля аллокаций (около 50 на операцию)
  приходится на транзакции Bitcask и одинакова для обоих движков. Абсолютный p99 у нового движка не хуже, чем у
  hashicorp: у hashicorp отношение ниже только потому, что медиана вдвое выше. Варианты — уменьшить аллокации
  в `bitcask.Tx` и в декодере транспорта или задать `GOMEMLIMIT`/`GOGC` в `cmd/bitkv`.
- **Отказ лидера за 2 × таймаут выборов.** Таймаут фолловера сам по себе случаен в диапазоне [1, 2) таймаута.
  Поэтому первая запись после падения лидера может прийти чуть позже двух таймаутов. Разделённые голоса,
  которые давали хвост до 3,7 таймаута, устранены.
- **Ожидание в очереди на пути «commit → apply»** из отчёта этапа 2 осталось. После исправления `wal.Sync` оно
  перестало быть главным ограничением.
