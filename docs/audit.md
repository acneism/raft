## Итог

Весь пакет `internal/raft` переписывается. Архитектура ТЗ (раздел 4.1) требует чистого ядра `Step/Tick/Ready/Advance`
без горутин, IO и системного времени. Текущий код устроен наоборот: состояние под одним мьютексом, HTTP-вызовы
и таймеры прямо внутри логики протокола. Переделать его постепенно не получится. Кроме того, в нём есть ошибки
безопасности (голос не сохраняется, неверный кворум при чётном числе узлов, потеря состояния при оборванной записи),
так что опираться на него как на эталон тоже нельзя.

Сохраняется немного:

- **правило «журнал кандидата не хуже»** (`election.go:135`) — переносится в ядро как есть;
- **табличные сценарии** из `types_test.go` — переносятся в тесты нового ядра;
- **`internal/config` (Raftfile)** — остаётся для демо-бинарника `cmd/node`, в библиотеку не входит;
- **`cmd/node` и HTTP `/status`, `/command`** — остаются как демо-клиент поверх нового `node`, не как транспорт Raft.

## Прочие ошибки

- `applyCommitted` шлёт в `applyCh` (буфер 100), который никто не читает. После 100 применённых записей горутина
  навсегда блокируется, и `stopCh` её не останавливает (`node.go:119`). Это ровно проблема G2 из ТЗ.
- `NotifyHeartbeat` (`types.go:106`) сбрасывает `votedFor` при равном терме, что позволило бы голосовать дважды
  в одном терме. Сейчас метод не вызывается — удалить.
- `replicateTo` берёт срез `n.log[nextIdx:]` под `RLock` и сериализует его уже после `RUnlock`. Параллельная обрезка
  и дозапись журнала перезаписывают тот же массив — гонка данных (`replication.go:34`).
- `SubmitCommand` выставляет `nextIndex = len(log)` фолловерам без подтверждений (`replication.go:199`). В итоге
  новая запись им не уходит, пока откат по одному не вернёт `nextIndex` назад.
- `Stop()` дважды вызывает `close` → panic. HTTP-сервер после `Stop()` продолжает менять состояние узла.
- Кандидат, получивший `AppendEntries` своего же терма, не становится фолловером сам — это делает цикл выборов
  через `heartbeatCh`, если сигнал не был съеден раньше.
